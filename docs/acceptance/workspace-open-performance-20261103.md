预热缓存后的只读补测：43份文件的原稳定指纹函数合计约1.3秒；该函数仍执行既有双次读取和文件标识检查。此值不是打开当时的冷缓存计时。准备阶段内部尚无逐子步骤耗时，不能据此断言29秒全部来自哈希、某个身份记录或某个文件。

日志中原生加载尾段约15.6秒没有子文件完成通知，最后一个开始通知为显示器零件；这段也可能包含总装收尾、显示或重建，不能全部归因于该零件。

## 有依据的优化方向

1. 文件准备后台化。缓存命中路径的 `PrepareWorkingCopyAsync` 在第一个未完成的 await 之前同步执行文件校验、身份记录和权限检查；async 方法不会自动转移这些工作。应将纯文件和元数据操作放入受限后台任务，保持 COM、原生打开、界面更新在所属线程，保留取消和并发保护。
2. 在不改变校验条件的前提下减少重复工作。现在准备阶段、清单绑定、取回显示标记和打开后分别读取/更新文件记录。先补齐各步骤计时，再合并确实重复的记录操作；纯显示时间可集中更新。完整性、版本、权限、本地修改保护、加载后真实来源核对仍须保留，不能只凭文件名或时间戳跳过核对。
3. 面板展开只处理展示。项目列表、关联和本地路径索引应复用现有结果，后台更新；补齐首次显示、状态刷新和实际绘制耗时，区分面板自身等待与图档打开阻塞。本次未抓到图标点击前后的准确调用栈，尚不能把该长卡顿归因于某一函数。
4. 原生加载单独量化。30.1秒发生在 OpenDoc6 内部，不能通过删减后台校验来宣称消除。先区分具体文件加载与总装重建/显示；轻化、大型设计审阅等模式影响编辑与结构可用性，需要单独确认，不自动改变。

优先建议1、2及必要计时。总耗时中本地准备约占43%，原生加载约占44%；实际收益必须用同一图档、相同加载模式前后对照，不承诺未经实测的百分比。
